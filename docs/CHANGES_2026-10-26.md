## 1. Remove the custom `Show_*` / `Rev_*` ad events (launcher)

**Why:** `logAdShow()` and `logAdRevenue()` in `AdsConfigManager.kt` had been commented out, but ~36 call sites still used them, so the build was broken.

**Important:** the old `logAdRevenue(format, place, adValue)` did **two** things:
1. logged a custom `Rev_<Format>_<Place>` event;
2. called `sendRevenue("${format.lowercase()}_${place.lowercase()}", adValue)`, which logs the standard Firebase `ad_impression`.

Deleting the calls outright would have **lost revenue tracking**, so:
- every `logAdShow(...)` call → **deleted**;
- every `logAdRevenue(fmt, place, v)` call → **replaced** with `sendRevenue("<fmt>_<place>", v)` (same placement key the old function used, e.g. `logAdRevenue("Inter","Splash",v)` → `sendRevenue("inter_splash", v)`; `place` variables → `"inter_${place.lowercase()}"`);
- `AdListener.onAdImpression()` overrides that only did `super.onAdImpression(); logAdShow(...)` → removed entirely. Overrides in `FullScreenContentCallback` keep their `Log.d` line;
- unused imports `android.os.Bundle` and `com.google.firebase.analytics.FirebaseAnalytics` removed from `AdsConfigManager.kt`.

**Files:** `config/AdsConfigManager.kt` (35 call sites), `ui/launcher/settings/LauncherMainSettingsActivity.kt` (1 call site).

**Porting checklist:**
- `grep -rn "logAdShow\|logAdRevenue" app/src` → handle each call as above.
- Delete the commented function bodies.
- Afterwards the grep must return nothing.

(Change 2 then changes `sendRevenue`'s signature again; port 1 and 2 together.)

## 2. `ad_impression` allow-list by ad unit ID (launcher + Flutter)

**Why:** `ad_impression` was controlled by ~20 per-placement Remote Config flags (`sendRevenueDashboardNative`, `sendRevenueVideoDownloaderInter`, …), and several were broken:
- launcher placement keys like `inter_splash` didn't match the lookup table (which expected `splash_inter`), so they fell through to `else -> true` and always fired;
- Flutter's `logAdRevenueEvent` skipped the check entirely;
- standalone Remote Config parameters never reached Flutter (only the JSON blob is passed over the channel).

**New rule (identical in both apps):**
```
fire ad_impression  ⇔  sendRevenueToAnalytics == true
                       AND ad.adUnitId ∈ adImpressionEventAllowed
```
- Missing or empty list → **nothing fires** (strict allow-list).
- Old per-placement `sendRevenue*` flags → **deleted**.
- Flutter `Rev_*` / `Show_*` events → **deleted**.

**Remote Config:** both keys go **inside the JSON parameter** (here `video_downlader_launcher_v2`, misspelling intended), so Flutter receives them through the existing `rawConfigJson` channel:
```json
"sendRevenueToAnalytics": true,
"adImpressionEventAllowed": ["ca-app-pub-xxx/111", "ca-app-pub-xxx/222"]
```

```kotlin
fun sendRevenueToAnalytics(adUnitId: String?, placement: String, revenue: Double, currency: String?, precision: Int) {
    val allowed = app.messages.config.AdsConfigManager.shouldSendAdImpression(adUnitId)
    Log.d("AdRevenue", "ad_impression [$placement] unit=$adUnitId allowed=$allowed revenue=$revenue $currency")
    if (!allowed) return
    val bundle = Bundle().apply {
        putString(FirebaseAnalytics.Param.AD_PLATFORM, "admob")
        putString(FirebaseAnalytics.Param.AD_SOURCE, "AdMob")
        putString(FirebaseAnalytics.Param.AD_FORMAT, adFormatOf(placement))   // real format, not the placement
        putString(FirebaseAnalytics.Param.AD_UNIT_NAME, adUnitId)              // standard GA4 param
        putString("ad_placement", placement)
        putDouble(FirebaseAnalytics.Param.VALUE, revenue)
        putString(FirebaseAnalytics.Param.CURRENCY, currency?.takeIf { it.isNotBlank() } ?: "USD")
        putInt("precision_type", precision)
    }
    FirebaseAnalytics.getInstance(instance).logEvent(FirebaseAnalytics.Event.AD_IMPRESSION, bundle)
}

/** Maps a placement key like "inter_splash" or "app_click_open" to its ad format. */
private fun adFormatOf(placement: String): String {
    val p = placement.lowercase()
    return when {
        "native" in p -> "native"
        "banner" in p -> "banner"
        "appopen" in p || "app_open" in p || p.endsWith("_open") -> "app_open"
        "inter" in p -> "interstitial"
        else -> "unknown"
    }
}
```
The old no-placement `sendRevenueToAnalytics(revenue, currency, precision)` overload was deleted.

## 3. `pr_appBigNative`: only request when the ad can be seen (Flutter)

**Why:** AdMob showed `pr_appBigNative` 7,294 requests → 2,033 impressions (**28.72% show rate**). Firebase showed `LOAD_APP_BIG_NATIVE_ONSPOT` 5,950 vs `Show_Native_VD_Search` 1,918 (32%). Causes:
1. `MessagesApplication.initFlutterEngine()` pre-warms the engine and runs Dart `main()` on **every process start**, so `HomePage` → `SearchPage.initState()` → `_refreshHomeBigNativeAd()` requested an ad that **nobody could see**. `_onAdsConfigUpdated()` requested again on every config sync.
2. A new request on every return to Home (`didPopNext`, tab switch), even when the ad on screen was seconds old.
3. The loading screen requested in `initState`, but extraction often finishes in under 1 s.
4. A single-slot cache with no expiry (native ads expire after ~1 h).

**Files:** `for_ads/ads/ads_load_util.dart` (`AppBigNativeAdPool`), `features/browser/views/search_page.dart`, `features/browser/views/Loadingscreen.dart`.

**Pool (`AppBigNativeAdPool`), final behaviour:**
- **Visibility gate:** with no cache hit, nothing in flight and the downloader not visible, the request is stored in a single `_pending` slot (latest screen wins) and **no AdMob call is made**. It's replayed when the downloader becomes visible (see change 4 for where visibility comes from).
- **Cache expiry:** `_cachedAt` is stored with the ad; a cached ad older than **55 min** is disposed instead of shown. All cache writes go through `_storeInCache()`.
- **Cache-only option:** `loadForScreen(..., allowNetwork: false)` delivers a fresh cached ad or calls `onFailed` immediately.
- **No duplicate requests:** `_isInFlight = true` is set **before** `await isInternetConnected()`, so a concurrent call joins the in-flight request.
- `detachScreen(tag)` also clears `_pending` for that tag.
```dart
static const Duration _cacheTtl = Duration(minutes: 55);
static ({String screenTag, Function(NativeAd) onLoaded, Function() onFailed})? _pending;

// loadForScreen order: purchase/invalid → cache (TTL) → allowNetwork? → not visible ⇒ _pending
//                      → register callbacks → in-flight ⇒ join → _isInFlight=true → internet check → load
```

**Home (`search_page.dart`):**
- `DateTime? _homeAdShownAt` is set when an ad is displayed.
- `_refreshHomeBigNativeAd()` returns early if an ad is on screen and is under **60 s** old (AdMob's minimum refresh interval). This covers `didPopNext`, tab switches and config updates.
- Refreshes when the downloader becomes visible: `AppBigNativeAdPool.downloaderVisible.addListener(_onDownloaderVisibilityChanged)`, removed in `dispose()`.

**Loading screen (`Loadingscreen.dart`):**
1. `loadForScreen(..., allowNetwork: false)`: show a cached ad instantly.
2. On miss: `Timer(2500 ms)`. Only if still mounted and no ad is shown, start a network `loadForScreen`. The timer is cancelled in `dispose()`.
   Fast extractions now make no request; slow ones (ApiHut fallback) still show an ad.

**Verify (logcat `tag:flutter message:AppBigNativeAdPool`):**
- Cold start on launcher Home: `⏸️🙈 Deferred request for SearchPage (downloader not visible)` and **no** `🚀📡 IN-FLIGHT START`.
- Swipe to the downloader: `👁️ Downloader visible = true` → `▶️👀 Firing deferred request` → exactly **one** `IN-FLIGHT START` (other triggers log `⏳🤝 IN-FLIGHT JOIN`) → `🎯✅ AD LOADED!`.
- Back to Home within 60 s: `🧊 Displayed ad is fresh enough`.

## 4. Downloader visibility comes from the launcher (Kotlin → Flutter)

**Why:** the first version of change 3 used `WidgetsBinding.instance.lifecycleState == AppLifecycleState.resumed`. On a device the pre-warmed engine reported **`resumed` during the onboarding intro**, with no view attached, so the ad was still requested. **Don't rely on Flutter's lifecycle state for a pre-warmed engine.**

**Reliable signal:** the downloader is shown by `VideoDownloaderContainerFragment` (`FlutterFragment.withCachedEngine`) on **page 0** of the launcher `ViewPager2` (`LauncherPagerAdapter`, `FragmentStateAdapter`). `FragmentStateAdapter` resumes **only the current page**, so the fragment being resumed means the downloader is on screen.

**Gotcha:** `LauncherHostFragment` sets the adapter (current item = 0) and only later, in `viewPager.post { setCurrentItem(initialTab) }`, jumps to the landing tab. Page 0 is briefly resumed at startup, so "visible" is **debounced by 400 ms**.

**`ui/launcher/downloader/VideoDownloaderContainerFragment.kt`:**
```kotlin
private val markVisible = Runnable { VideoDownloaderEngineHelper.setDownloaderVisible(true) }

// ViewPager2 resumes only the current page, so resumed == on screen. The
// launcher briefly selects page 0 before jumping to its landing tab, hence
// the short delay before reporting visible.
override fun onResume() {
    super.onResume()
    view?.postDelayed(markVisible, VISIBLE_DEBOUNCE_MS)
}

override fun onPause() {
    view?.removeCallbacks(markVisible)
    VideoDownloaderEngineHelper.setDownloaderVisible(false)
    super.onPause()
}
// companion: private const val VISIBLE_DEBOUNCE_MS = 400L
```

**`ui/videodownloader/VideoDownloaderEngineHelper.kt`:**
```kotlin

// in initMethodChannel's when(call.method):
"isDownloaderVisible" -> result.success(isDownloaderVisible)
```

**`video_downloader/lib/main.dart`** (in the `nativeChannel` handler, plus a pull at startup in case the engine started late):
```dart

  final args = call.arguments;

...
```

(Add `import 'for_ads/ads/ads_load_util.dart';`.)

**Pool:** `static final ValueNotifier<bool> downloaderVisible = ValueNotifier(false);` `_isVisible` reads it. `setDownloaderVisible(true)` replays `_pending`. Home listens to the notifier instead of an `AppLifecycleListener`.

**Porting checklist:**
- Find which native screen hosts the Flutter view (fragment in a pager, activity, …) and send visible on `onResume` (debounced) and hidden on `onPause`.
- If the host isn't a `ViewPager2` page, `onResume` may not mean "on screen". Check the lifecycle there.

## 5. Downloads: block search pages and unsupported sites (Flutter)

**Why:** Firebase (24–26 Oct): `download_click` 260 → `download_unknown` **251** → `download_completed` **4**.
- The browser home page is Google; typed text becomes `google.com/search?q=…`.
- An unrecognised host gives `"unknown"`, and `isValidVideoUrl`'s `default:` branch accepted **any URL with a path**, so the Google search page passed.
- `VideoExtractorManager` skipped SMDownloader (`unsupported_platform`) and called ApiHut with `"type": "unknown"`, which always fails.
- Extra bug: `url.contains("x.com")` matched `netflix.com`, `dropbox.com`, `box.com` (also `ted.com`, `vk.com`).

**Decision:** on an unrecognised site, **don't start a download; show a hint**. Search pages are always blocked.

### `features/browser/utility/platform_detector.dart`
- **Host-based detection:**
  - `hostOf(url)`: lowercase host without `www.` / `m.` / `mobile.`.
  - `_hostIs(host, domain)` = `host == domain || host.endsWith('.$domain')`.
  - A `_platformHosts` table, e.g. `("twitter", ["twitter.com","x.com"])`, `("youtube", ["youtube.com","youtu.be"])`, `("facebook", ["facebook.com","fb.watch","fb.com"])`, `("instagram", ["instagram.com","instagr.am"])`, `("threads", ["threads.net","threads.com"])`, `("bilibili", …)`, `("chzzk", ["chzzk.naver.com"])`, `("naver tv", ["tv.naver.com"])`, `("linkedin", ["linkedin.com"])`, and so on; same platform names as before.
  - Pinterest country domains: any host with a `pinterest` label, plus `pin.it`.
- **`unwrap(url)`:** Google redirect `google.*/url?q=<target>` (or `url=`) and AMP `google.*/amp/s/<target>` → the real target URL.
- **`detectPlatform(url)`** = table lookup on `hostOf(unwrap(url))`, else `"unknown"`.
- **`rejectReason(url, platform)`** returns `null` if downloadable, otherwise:
  - `'search_page'`: empty URL, `about:blank`, no host, or a search host (`google.*` any label, `yandex.*`, `bing.com`, `yahoo.com`, `duckduckgo.com`, `baidu.com`);
  - `'unsupported_site'`: platform empty or `"unknown"`;
  - `'not_a_post'`: a known platform whose existing per-platform path rule fails (feed, profile, home).
- The old rule body was renamed `_matchesPostRule`. Its `default:` branch **no longer accepts generic URLs**.
- `isValidVideoUrl(url, platform) => rejectReason(url, platform) == null` is kept for compatibility.

### `features/browser/views/Browser.dart` (download FAB `onPressed`)
```dart

  FirebaseAnalyticsService.logDownloadRejected(reason: rejectReason, platform: effectivePlatform, url: targetUrl);
  showToast(rejectReason == 'not_a_post' ? 'please_play_or_open_post'.tr : 'open_video_on_supported_app'.tr);
  return; // no task, no loading screen, no ApiHut call
}
```

## 6. Onboarding intro image: ~100 MB decode (launcher)

**Why:** `res/drawable/img_intro_1.png` is **1284×2182 px, 2.3 MB** in the density-less `drawable/` folder, which Android treats as **mdpi** and scales up on decode:
- xxhdpi ×3 ≈ 3852×6546 ≈ **100 MB** bitmap;
- xxxhdpi ≈ 179 MB, which can crash with "Canvas: trying to draw too large bitmap" or run out of memory.

It's decoded on the main thread on the **first onboarding screen** (`OnboardingFragment.kt:71`). Firebase: 445 users lost before "Get Started".

**Fix:** `git mv res/drawable/img_intro_1.png res/drawable-nodpi/img_intro_1.png`. No code change. The `ImageView` is `match_parent` width with `scaleType="centerCrop"`, so it looks the same; it just decodes at its real size (~11 MB).

**Porting checklist:**
- Find large raster images in `res/drawable/`:
  ```bash
  for f in res/drawable/*.png; do s=$(stat -c %s "$f"); [ $s -gt 200000 ] && echo "$s $f"; done
  ```
- For each, check how it's displayed: `centerCrop`/`fitXY`/`match_parent` → safe to move to `drawable-nodpi`. `wrap_content` → its on-screen size would change, so downscale instead.

**Same problem, NOT fixed yet:** `bg_splash_video_downloader.png` (1284×2778, splash screen), `ic_splash_logo.png` (2048×2048), `img.png` / `img_1.png` (1170×2532), all in `res/drawable/`.

## 7. Flutter interstitial: infinite loop (Flutter)

**Why** (`for_ads/ads/ads_load_util.dart`):
- `showInterstitial()` called `loadAndShow()` when `!isAdLoaded`.
- `loadAndShow()` set `isAdLoaded = false` and, because `_interstitialAd != null`, called `showInterstitial()` again.
- `_interstitialAd` was **never set to null** after dispose.

So after one ad had been shown, a failed preload (no fill, offline) made the two functions call each other forever, opening `loadingScreen.show()` every pass until a stack overflow. The user saw a stuck "Showing Ads" overlay or a crash, and the tap did nothing. Ads were also disposed 2–3 times, and `.show()` was called before `fullScreenContentCallback` was set.

**Fix:**
```dart
/// Drops the preloaded interstitial (disposing it once) so a stale or
/// already-shown ad is never reused.
static void _clearPreloadedInterstitial() {
  final old = _interstitialAd;
  _interstitialAd = null;
  isAdLoaded = false;
  old?.dispose();
}
```
- **`loadPreInterstitialAd`:** calls `_clearPreloadedInterstitial()` before loading; `onAdFailedToLoad` sets `_interstitialAd = null; isAdLoaded = false;`.
- **`showInterstitial`, preloaded path:**
  - take ownership with `final preloadedAd = _interstitialAd; _interstitialAd = null; isAdLoaded = false;`;
  - set `onPaidEvent` and `fullScreenContentCallback`, **then** `preloadedAd.show()`;
  - on dismiss or fail-to-show: `ad.dispose()` once, then `loadPreInterstitialAd(adId: interstitialId)`, then `onDismissed()`.
- **`loadAndShow`:**
  - **never** calls `showInterstitial`;
  - calls `_clearPreloadedInterstitial()`, sets `interstitialId = adId`, shows the loading screen, loads a fresh ad;
  - uses the loaded ad as a local (not stored in `_interstitialAd`), sets its callback, then shows it.
- Same ads, placements, log lines and analytics events as before.

**Verify:** show one interstitial in the downloader, turn on airplane mode, tap a tab. There should be no stuck overlay or crash, and the action should proceed.

## 8. Language "Done" now opens the launcher during onboarding (launcher)

**Why:**
- `OnboardingActivity.proceedToNextScreen()` calls `prefs.setOnboardingDone(true)` **before** opening Language.
- `LanguageSelectionActivity` had `isFromSettings = extra("from_settings") || prefs.isOnboardingDone()`, which was therefore always true during onboarding.
  - So after "Done" it only called `finish()` instead of starting `LauncherActivity`. The app appeared to close, or Android cold-started the launcher through HOME.
  - It also always skipped the launcher ad preloads (`isFirstLaunchOnboarding` was always false).
- Firebase: language done 677 vs set as launcher 613.
- Some Settings entry points (`LauncherMainSettingsActivity:240`) open Language **without** the `from_settings` extra, so the extra alone isn't enough.

**Fix** (`ui/activity/LanguageSelectionActivity.kt`), read **before** `onCreate` sets `languageSelected = true`:
```kotlin
// Onboarding marks itself done before this screen, so that flag can't tell
// the two apart. A language is only already chosen when coming from
// Settings; read it before it is set below.
isFromSettings = intent.getBooleanExtra("from_settings", false) || (prefs?.isLanguageSelected() == true)
...
val isFirstLaunchOnboarding = !isFromSettings   // was: !isFromSettings && !prefs!!.isOnboardingDone()
```

**Verify:** on a fresh install, "Done" goes straight to the launcher, and logcat shows `[LANGUAGE_DONE] ... Preloading Native Dashboard Ad` and `FLOW_CHECK 🚀 [LANGUAGE_DONE] ... Launching LauncherActivity`. Settings → Language → Done just closes the screen.

## Lessons and gotchas (read before porting)
1. **A pre-warmed `FlutterEngine` can report `AppLifecycleState.resumed` with no view attached.** Use a native-driven visibility signal (change 4).
2. **`ViewPager2` briefly resumes page 0** before `post { setCurrentItem(...) }`. Debounce "visible".
3. **Only the JSON Remote Config parameter reaches Flutter** (`rawConfigJson`). Standalone parameters are applied only in the launcher.
4. **Native ads have no `adUnitId`.** Keep the ID used in `AdLoader.Builder`.
5. **Images in `drawable/` are treated as mdpi** and scaled up by density. Put large rasters in `drawable-nodpi` or a density folder.
6. **KSP crash `NoSuchFileException …kspCaches…`:** two Gradle builds ran at once. Fix: delete `app/build/kspCaches` and run one build only (`gradlew --stop` if needed).
7. **Build blocker seen earlier:** `google-services.json` must contain a client whose `package_name` equals `applicationId`.
8. **Dart translation strings:** escape `'` inside single-quoted strings.
9. **Logs are tagged `flutter`** (`showLog` → `print("LOG >> …")`). Logcat filters used:
   - big native ads: `tag:flutter message~:"AppBigNativeAdPool|Home Native Ad|Loading Screen Ad"`
   - downloads: `tag:flutter message~:"URL_FILTER|DOWNLOAD_|Analytics\] Download"`
   - extraction: `tag:flutter message~:"SMDownloader|ApiHut|Extractor|Download failed"`
   - launcher revenue: `adb logcat -s AdRevenue`
